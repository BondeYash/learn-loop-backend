## Authentication provider decision

**Existing Mongo auth + Resend (or another transactional provider):** preserves IDs, course relationships and the current cookie flow. Mail delivery does not itself provide invitations or verification; implement and test tokens, redemption, roles and recovery in this backend. Use the provider's verified sending domain and bounded delivery flow. This is the lower-disruption option for this codebase, not a completed selection.

**Clerk:** replace frontend auth flows and backend session verification, explicitly validate authorized parties, map Clerk identities onto stable Mongo user IDs, keep course authorization on the server, verify/idempotently process identity webhooks, and rehearse migration/rollback. A widget alone is insufficient. Clerk has a free hosted tier and open-source SDKs; that is not a self-hostable identity backend. Its production invite-only restriction requires a paid plan. Do not assume free invite-only onboarding. See [access restriction documentation](https://clerk.com/docs/guides/secure/restricting-access), [pricing](https://clerk.com/pricing), and [backend authentication](https://clerk.com/docs/reference/backend/authenticate-request). No provider is selected or configured in this release.

Render's [free service documentation](https://render.com/docs/free) states idle sleep and blocking of outbound SMTP ports 25/465/587; verify the actual service plan. If using free Render, an HTTPS email API avoids those SMTP ports, while always-on availability remains a separate hosting decision.

Execution sequence: choose student admission, mail provider, availability budget, retention and concurrency targets → close P0 access/abuse gaps → prove hosted recovery and E2E → operate a small invited pilot with monitoring → complete P1 measured improvements before expanding. Current hosting limits, backup settings and email domain ownership remain account-level unknowns until verified.
