# Authored quizzes and mock tests

Owners and administrators can author chapter quizzes and timed course mock tests for any course. A chapter is an existing course module; no official questions, exam promises or CCC-specific question bank is supplied. Drafts can have no questions. Publishing requires complete question text, 2–6 distinct options, one correct answer and an explanation. Topic tags are optional author-defined text. Quiz timers are optional; mock timers are required.

## API and access

All routes require the existing session and role checks. Authoring uses `requireCourseOwner`; learner list/start/answer/submit/result/history use `requireCourseAccess`, retaining publication/archive, private assignment, explicit public enrollment and current-mode paid entitlement. There is no anonymous assessment or public-sample exception.

- Owner/admin: `GET /api/courses/:courseId/assessments/manage`, `POST /api/courses/:courseId/assessments`, `PUT /api/courses/:courseId/assessments/:id`.
- Learner: `GET /api/courses/:courseId/assessments`, `POST /api/assessments/:id/attempts`.
- Own attempt: `GET /api/assessment-attempts/:id`, `PUT /api/assessment-attempts/:id/answers`, `POST /api/assessment-attempts/:id/submit`.
- Own history: `GET /api/courses/:courseId/assessment-attempts?page=1`, 20 entries per page.

Authoring bodies include `title`, `kind` (`quiz`/`mock`), `module` for a quiz, `durationMinutes` (integer or null for untimed quiz), `status` (`draft`/`published`) and `questions`. Each question contains `prompt`, `options`, `correctIndex`, `explanation` and optional `topic`. Updates must include the last received `version`; conflicting edits return 409. Answer bodies contain `questionIndex` and `optionIndex`; null clears an answer only in an attempt using delayed feedback. Start/submit ignore client-supplied answers, scoring, timestamps, feedback policy and ownership.

## Integrity and limits

Every attempt captures an immutable question/version/feedback-policy snapshot. Drafting or editing stops new attempts as appropriate, while existing attempts retain their original questions and may continue while course entitlement remains valid. Removing a chapter prevents new quizzes on that chapter; existing attempt snapshots are retained. Student list/history responses omit keys and explanations. Active new mocks reveal a correct index only for each question the student has already answered; unanswered questions remain private. Chapter quizzes and older attempts expose no active keys. Only the student's own ended attempt exposes its explanation review. Snapshots and authored questions are excluded from default model projections, with explicit response serializers at the protected endpoints.

A unique database index permits one active attempt per student/assessment, so concurrent/retried starts resume it. Deadlines are server timestamps; MongoDB server time prevents late answer writes. Refresh does not restart the timer. Expired attempts finalize when an attempt/history/start/answer/submit endpoint next observes them; there is no background timer service. Submission is idempotent, and revision-based compare-and-swap scoring includes accepted answers racing with submission. Clients cannot overwrite an ended result.

Limits are 40 assessments per course, 40 questions each, 2–6 options, 1–180 timed minutes and 100 attempts per learner/assessment. Unique numbered slots enforce the assessment/attempt caps during concurrent creation. Drafts count toward the course limit; assessment deletion/reclamation is outside this slice. Text limits are 160 title, 1200 prompt, 400 option, 2000 explanation and 80 topic characters. Each correct answer earns 1; incorrect/unanswered earns 0. No negative marking or pass/readiness threshold is configured.

Own history aggregates explicit tags from the latest 100 ended attempts. Tags below 70% correct form the weak-topic summary; untagged questions are excluded. This summarizes practice on authored question versions and does not establish official exam readiness. Lesson completion stays in existing `Progress`; quiz submission does not mark a lesson or course complete. Archive preserves assessments and attempts; existing permanent course purge removes them.

## Mock-test usability and first-save recovery — 2026-10-06

The original timed assessment/scoring subsystem remains authoritative. This increment makes it easy to reach and use: the instructor course card and course header link to mock management; a distinct **Create mock test** action opens a timed course mock (30 minutes initially, editable 1–180) without a chapter requirement. Mock tests and chapter quizzes have separate lists. Publishing a test does not publish the course or grant student access. The UI explains an unshared course; ownership, publication/archive, private nomination/public enrollment and any current-mode paid entitlement still apply.

New UI first saves send a stable UUID `requestId`. The server validates and hashes it, stores a private creation fingerprint and enforces a unique partial course/token index. Repeated/concurrent identical first saves return one saved test, including when the accepted response was interrupted. Changing an already accepted creation payload with the same UUID returns 409 with instructions to reload the list and edit the saved test. Subsequent edits retain existing version checks; old records/clients without the field remain compatible. Tokens/fingerprints never enter owner or learner DTOs. Startup's existing `Assessment.init()` awaits the new index; no data migration or seed is required.

Learners have a direct **Mock tests** entry from an eligible course card/header. Numbered question navigation identifies answered/unanswered questions and the current question. Answer saves, immutable snapshots, server deadlines/scoring, own history, retry-safe start/submit and hidden keys are unchanged. Initial status states that no answers are saved instead of implying an answer was saved. Switching courses clears the previous course's author/student screen; denied owner reads clear cached editors.

`tests/assessments.test.js` now also reproduces the former duplicate-first-save bug and verifies four concurrent retry-aware saves yield one record, changed payload conflict, owner/admin scope, private request metadata and edits/retries. The focused suite passes 10 tests; full backend verification passes 133 tests. The paired frontend's `tests/mock_test_e2e_browser.py` uses the actual login UI, cookie sessions, Express API and disposable local MongoDB: instructor draft/publish/edit → entitled student answer/resume/submit/result/history/timeout, accepted-response interruption, double clicks, validation, version snapshots, keys, other user/course scopes and both themes/mobile/zoom. API responses are forwarded, not mocked. A fixture command shortens only a synthetic attempt deadline to test expiry; production minimum duration is unchanged. `tests/mockBrowserFixture.js` requires test mode, a specific loopback frontend and hard-coded loopback MongoDB with a random disposable DB. It cannot choose a production connection string. It drops its own DB on exit.

Production course questions, students, prices, visibility and payment/provider settings were not changed. Local authenticated end-to-end success is stronger evidence than isolated UI mocks, but does not certify production authenticated acceptance, deployments, provider payment readiness or load capacity.

## Imported-question review — 2026-10-06

Question bodies may contain `importReview: {source, flags, checked, confidence?}`. Source is nonempty text up to 160 characters; flags are 1–10 known values (`table`, `pdf_text`, `ocr`, `low_confidence`, `layout`, `diagram`, `separate_key`, `missing_key`, `missing_explanation`, `manual`); checked is a boolean; optional confidence is finite 0–100. Drafts persist unfinished imported content within existing field limits. Publishing rejects unchecked imported questions and still requires complete text, distinct options, a correct answer and an explanation. Owners/admins receive this metadata; student list/active/result/history DTOs omit it. Authors are responsible for reviewing their own answer keys. The API does not receive original import files or run OCR, macros or formulas.

The paired frontend supports bounded `.pdf`, `.xlsx` and UTF-8 `.csv` extraction, local English/Hindi OCR, source/low-confidence warnings, editable groups of five and explicit append/replace confirmation. It only sends converted questions using these existing owner-protected routes after Save/Publish. No data migration, new entitlement exception or provider setting is required. The full backend regression suite passes 134 tests; the additional import review case covers draft/reload, checked/unchecked and malformed publication, foreign owner denial, student metadata/key privacy and immutable attempt results. The local browser fixture additionally supports expiring only its synthetic owner's sessions to test importer unmount/cancellation; it remains test-mode/loopback-only.

## Immediate mock-answer feedback — 2026-10-07

The server chooses `snapshot.feedbackMode: "after_answer"` for new mock attempts and `"after_submit"` for chapter quizzes. Missing policy on a stored attempt defaults to `after_submit`; no migration changes the rules of an existing attempt. Assessment lists advertise the policy for new attempts, while the own-attempt DTO reports the immutable policy actually in effect. Clients cannot choose it in start or answer requests.

For immediate feedback, the first answer is saved atomically only while that answer is null, the attempt is active and the MongoDB server deadline has not passed. A repeated identical choice returns the saved answer without changing its revision. A different choice returns 409; clearing returns 400. Concurrent different choices produce one accepted answer. Answer/submit races retain the existing revision-based final scoring, so accepted first choices cannot disappear from a submitted result. Quizzes and legacy attempts retain editing and clearing before submission.

The active immediate-feedback DTO has one `feedback` entry per question: null when unanswered, otherwise `{correctIndex, selectedIndex, correct}` derived from the saved answer and immutable snapshot. The question objects still contain only prompt/options/topic; explanations and import-review metadata remain withheld. Own student identity and current course entitlement are checked for each read/write. Instructor/admin authoring permissions do not confer access to another learner's attempt. Final result review, timing, scoring, history and lesson completion retain their original behavior.

`tests/assessmentFeedback.test.js` adds isolated real MongoDB/HTTP coverage for server policy, scoped feedback, identical retries, forbidden edits/clears, concurrent first choices, answer/submit races, unchanged snapshots and first-choice final scoring, legacy rules, chapter quizzes, deadlines and learner/role/entitlement denial. The focused feedback/assessment run passes 19 tests and the full backend suite passes 142. The paired frontend's real browser test also passes correct/incorrect feedback, keyboard/mobile/theme layouts, reload/Back, retry/conflict/stale-response handling, unanswered/final scoring and expired sessions. The frontend and backend must be deployed together; all changes remain local until separately authorized publication. The fixture's new session-expiry action affects only its synthetic student in its disposable loopback database.
